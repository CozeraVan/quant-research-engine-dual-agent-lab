# Local Backtest Console Design

**Goal:** Build a local browser-based console for the existing QRE backtest engine so a user can edit strategy YAML, adjust backtest parameters, run single-symbol / batch / shared-cash simulations, inspect outputs, and reopen prior runs without working only through Codex or the terminal.

**Context:** The current engine already supports:

- YAML strategy specs
- CLI backtests for `backtest-single`, `backtest-batch`, and `backtest-shared`
- local PostgreSQL market data reads
- durable output directories with report manifests
- run-history style reproducibility via the existing report/run manifest patterns

This design keeps that engine intact and adds a thin GUI layer on top.

## Product Shape

The first release is a **local web console**:

- runs on Ubuntu now
- should remain usable on macOS and Windows later
- does not aim to be visually polished
- prioritizes clarity, file-based reproducibility, and low friction

The console is not a public SaaS app and not a heavyweight desktop product. It is a local control surface for the existing backtest workflow.

## Recommended Approach

Use a Python web app as the front end to the existing engine.

Recommended stack:

- `qre gui` CLI command to launch the console
- Python web server inside the repo
- server-rendered pages for forms, tables, and run history
- plain YAML text editing as the strategy input method
- local filesystem storage for history and templates in version 1

Why this approach:

- matches the current Python-first repository
- works cross-platform without OS-specific GUI packaging
- can reuse the existing backtest modules directly
- can fall back to the existing `qre` CLI execution path if needed

## User Experience

The first screen should be the working screen, not a landing page.

Layout:

- strategy YAML editor
- backtest parameter panel
- run controls
- result summary and artifact viewer
- run history list with rerun actions

Primary workflow:

1. open the local console
2. load or paste a strategy YAML file
3. adjust dates, symbols, backtest type, capital, risk controls, and output location
4. validate the YAML
5. run the backtest
6. inspect summary, orders, trades, equity curve, and manifest
7. save or rerun the configuration from history

## Strategy Editing Contract

First release strategy editing is **YAML text first**.

The console must:

- load strategy YAML from file
- allow inline editing in a text area or code-like editor
- validate against the existing `StrategySpec` parser before execution
- show parsing and validation errors inline
- allow saving the current YAML as a reusable template

Non-goals for v1:

- drag-and-drop strategy composition
- visual indicator graphing inside the editor
- form-driven strategy authoring as the primary input

## Run Orchestration

The console should support all three current backtest modes:

- single-symbol
- batch
- shared-cash

The user can choose the runner:

- default path: direct Python module call into the existing backtest engine
- fallback path: invoke the existing `qre` CLI as a subprocess

This dual path keeps the first version fast while preserving a stable fallback for debugging and future portability.

Each run should produce a durable local record containing:

- the YAML strategy snapshot used for the run
- the resolved backtest parameters
- the execution mode
- timestamps and status
- output directory path
- the result summary
- a pointer to the full artifact set

## Local Storage

Version 1 stores history in the local filesystem.

Suggested structure:

- `outputs/gui-console/templates/` for saved strategy templates
- `outputs/gui-console/runs/<run-id>/strategy.yaml`
- `outputs/gui-console/runs/<run-id>/request.json`
- `outputs/gui-console/runs/<run-id>/status.json`
- `outputs/gui-console/runs/<run-id>/stdout.log`
- `outputs/gui-console/runs/<run-id>/artifacts/`

The same schema should later be movable to PostgreSQL without changing the user-facing workflow.

## History And Re-run

History is part of the first release.

The console should support:

- listing saved runs
- filtering by strategy name, date, and backtest type
- reopening a past run into the editor
- re-running a past configuration without manual reconstruction

## Result Viewer

The first release should expose the full report output, not only a summary card.

Show these artifacts:

- `summary`
- `orders`
- `trades`
- `equity`
- `report_manifest`
- any output files generated by the backtest

The result page can be plain and table-oriented. The main requirement is that the user can understand what happened without leaving the browser.

## Error Handling

The console should fail early and clearly for:

- invalid YAML
- unsupported strategy fields
- missing required parameters
- backtest engine exceptions
- CLI fallback failures
- missing output directories

Errors should be visible in the GUI and also recorded in the run history record.

## Implementation Boundaries

Keep the GUI layer separate from the backtest engine:

- GUI handles input, orchestration, persistence, and display
- backtest modules remain the source of trading logic
- report manifests remain the source of artifact discovery

Do not rewrite the engine to fit the GUI. The GUI should adapt to the engine that already exists.

## Scope Control

In scope for v1:

- local web console
- YAML file upload/edit/save
- single/batch/shared-cash run control
- history on local filesystem
- rerun from history
- full result artifact display

Out of scope for v1:

- cosmetics / visual polish
- multi-user support
- authentication
- PostgreSQL history store
- distributed execution
- job queue infrastructure
- strategy drag-and-drop builder

## Acceptance Criteria

- The user can open a local web console and edit a YAML strategy.
- The user can load an existing YAML file or save a template.
- The user can run single-symbol, batch, and shared-cash backtests from the GUI.
- The user can choose direct module execution or CLI fallback.
- The console stores run history locally on disk.
- The user can reopen and rerun a past configuration.
- The console shows summary, orders, trades, equity, and manifest artifacts.
- The implementation remains cross-platform and does not depend on Ubuntu-only features.

## Open Questions Resolved

- Strategy editing method: YAML text first.
- Execution method: module call by default, CLI fallback retained.
- Supported backtest modes: single, batch, shared-cash.
- History storage: local filesystem first, PostgreSQL later.
- Result depth: full report artifact display.
