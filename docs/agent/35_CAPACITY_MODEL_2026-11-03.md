## 1. 三项实测核对：时间与内存的关系

### 1.1 原始数据（全市场 5201 只 × 2009-01-05~2026-10-30，约 17.8 年 ≈ 92,578 股年）

| 指标 | item1 NL SMA5×SMA200 | item2 wizard RSI14 | item3 NL MACD |
|---|---:|---:|---:|
| 执行时长 | 3854 s | 2571 s | 4312 s |
| 交易笔数 | 76,511 | 18,978 | 504,183 |
| worker RSS 峰值 | 6.38 GB | 6.30 GB | **13.97 GB** |
| MemAvailable 最低 | 13.47 GB（含 pytest 污染窗） | 14.32 GB | **6.28 GB** |
| 分段（逐股/聚合/报告/序列化上传） | 3261 / 361 / — / 229 s | — / 235 / — / — s | 2394 / **1296** / 300 / 322 s |
| 本地产物 | 1.01 GiB | 0.85 GiB | 1.52 GiB |

### 1.2 时间结构（与 31 号文档模型一致，回代误差 −17% ~ +7%）

`T ≈ T_fixed + R_sy × stock_years + R_trade × trades`（31 §2.1）在三项上回代偏差
−17%/+7%/−7%，量级正确。补充两点 31 号未展开的实测事实：

- **逐股速率本身随策略变化**：item1 3261 s / 92,578 ≈ 0.035 s/股年，item3 2394 s /
  92,578 ≈ 0.026 s/股年，相差 35%（信号条件复杂度/因子列数不同）。`R_sy` 不是常数，
  应按策略族分别取。
- **聚合阶段随交易笔数放大且可成为主瓶颈**：item3 聚合 1296 s 是 item1（361 s）的
  3.6×、item2（235 s）的 5.5×；笔数多 6.6×（vs item1）时间多 3.6×——同向但**不是**严格
  比例（亚线性），样本只有 3 点，不足以定标度。

### 1.3 内存结构：峰值在聚合/报告/序列化，不在逐股计算

item3 的 RSS 曲线（27 §7.5，采样 3,829 行）是最关键的一条证据：

```
逐股阶段        0.75–1.0 GB（05:00–05:33，约 40 分钟稳定低位的平台期）
聚合起步(05:33) 冲到 4.7 GB
聚合中段        3.1–3.2 GB（05:40/05:50）
绘图/报告(05:55起) 6–9.9 GB
峰值(05:57)     14.3 GB（RSS 13.97 GB）
上传序列化(06:01) 14.06 GB（MemAvailable 同时触底 6.28 GB）
归零(06:04:56)
```

结论（与 P0-10 立项描述一致）：**内存峰值出现在「聚合 → 绘图/报告 → 序列化」三段，
随交易笔数/聚合规模放大，而非逐股计算阶段**。逐股阶段 RSS 仅 ~1 GB，说明分块流式
（R-MEM-001 规则 1）在计算段是有效的；未分块的是尾段。

### 1.4 样本量与诚实性边界

- 仅 3 个实测点，且 **stock_years 三项完全相同（92,578）**——「固定开销」与「股年项」
  在数学上不可分离；能分离的只有交易笔数一个自变量。
- item1 有 03:14–03:17 pytest 污染窗（资源曲线该段不可作独占基线）。
- 单机、单 PG 配置、单策略族各一个样本；`R_trade` 实际由 item3 单点估计
  （31 号文档已如实记录该局限）。
- 因此本文**不做精确拟合、不声称线性关系已证实**；内存模型采用「实测包络 + 余量」，
  只服务于**准入预算**（宁可高估），不用于预测。

## 2. 保守内存估算模型（准入预算用）

### 2.1 模型形式

```
PeakBudget(trades) = Envelope(trades) × Headroom
Envelope(trades)   = max{ 实测峰值 : 实测笔数 ≤ trades }        （单调阶梯，测量点上取实测值）
                     + 17.7 KB/trade × (trades − 504,183)       （仅 >504k 的外推，未验证）
Headroom           = 1.25
```

- `trades` **未知**（提交时，全市场全期、策略未实测）：直接取最坏实测包络
  **13.97 GB × 1.25 ≈ 17.5 GB**。
- `trades` **已知/可估**（同策略族有实测笔数，或小样本外推）：按阶梯取值。

### 2.2 为什么不用「固定 + 股年 + 笔数」的线性式做准入

用 item1/item3 两点拟合（唯一可分离的自变量是笔数）：

```
slope     = (13.97 − 6.38) GB / (504,183 − 76,511) ≈ 17,745 B/笔 ≈ 17.3 KiB/笔
intercept = 6.38 − 76,511 × 17,745 B ≈ 5.02 GB
```

回代（误差按实测值归一）：

| 项 | 模型估算 | 实测 | 偏差 |
|---|---:|---:|---:|
| item1 | 6.38 GB（拟合点） | 6.38 GB | 0%（构造） |
| item2 | **5.36 GB** | **6.30 GB** | **−15%（低估）** |
| item3 | 13.97 GB（拟合点） | 13.97 GB | 0%（构造） |

item2 被低估 15%，且换个读法更别扭：若以低笔数的 item2 为「基座」6.30 GB，则 item1
（76.5k 笔）只 +0.08 GB（≈1.1 KiB/笔），item3（504k 笔）却 +7.67 GB（≈15.7 KiB/笔）——
两个斜率差 14 倍。三种可能（阈值效应/超线性/聚合结构临界）无法用 3 点区分。
**结论：笔数→内存的线性关系未证实；线性式只可做数量级筛查，不可做准入保证。**
准入统一用 §2.1 的包络模型（测量点上取实测、外推标注未验证、统一 ×1.25 余量）。

### 2.3 预算表（回代与保守上限）

| 场景 | 笔数量级 | Envelope | ×1.25 预算 | 回代误差说明 |
|---|---:|---|---:|---|
| smoke / ≤5 只小样本 | ~0 | — | 1.5 GB（R2 轻槽预算，实测 smoke 产物 391 KB，秒级） | 实测支撑充分 |
| 全市场低换手（item2 类） | ≤ 2 万 | 6.30 GB | **7.9 GB** | 实测点 |
| 全市场中换手（item1 类） | ≤ 8 万 | 6.38 GB | **8.0 GB** | 实测点；线性式会得到 6.38（巧合吻合） |
| 全市场高换手（item3 类） | ≤ 50 万 | 13.97 GB | **17.5 GB** | 实测点；线性式构造吻合 |
| 全市场未知策略 | 未知 | 13.97 GB（最坏包络） | **17.5 GB** | 无实测，按最坏包络 |
| > 50 万笔 | 外推 | 13.97 + 17.7 KB×(t−504,183) | 同左 ×1.25 | **未验证外推，仅方向性参考** |

### 2.4 可行性核查（本机 23.5 GiB，压测期 PG RSS 峰值 5.4 GB）

- 单个 item3 级任务：实测可跑（MemAvailable 触底 6.28 GB，即系统+PG+单任务后剩 ~6.3 GB）。
- **两个** item3 级任务：≈ 28 GB > 23.5 GiB 物理 → 必 OOM（cgroup 未生效时=全局 OOM
  killer，job#71 事故模式）。
- worker 实际可用预算 ≈ 23.5 − 5.4（PG 峰值）− ~2.5（系统/浏览器/日常）≈ **15.5 GiB**：
 一个未知全市场任务（实测 13.97 GB）之后只剩 ~1.5 GB，**恰好再容一个轻任务，容不下第二个重任务**。
- 17.5 GB 的保守预算 **超过 R-MEM-001 规则 2 的子进程上限（≤物理 50% ≈ 11.7 GiB）**，
  也超过当前 `QRE_WORKER_CHILD_MEM_GB` 默认 14 GB——即「未知全市场全期」在当前机器上
  **不存在满足锁定要求的预算**（见 §6 待裁决 1）。另外 item3 实测 13.97 GB 本身已越过
  R-MEM-001 的 11.7 GiB 线（压测时靠 RLIMIT_AS=14G 与运气未死），这是既成事实，
  必须在裁决项中显式处理，不能默默继续。

## 3. 调度建议（R2 失效分析与多重约束准入）

### 3.1 现有 heavy 6500MB / 3 槽为何失效

| # | 失效点 | 证据 |
|---|---|---|
| 1 | 闸门看**认领瞬间** MemAvailable，任务 40–70 分钟后才到峰值 | item3 准入时 driver 前置检查 MemAvailable≈22.3 GB，三槽全放行；峰值在 05:57 |
| 2 | 所有 heavy 任务按**统一 6 GB 预算**假设，无按任务峰值的区分 | R2 文档「重槽预算 6G/个」；item3 实测 13.97 GB，超假设 2.3× |
| 3 | **无在途记账**：不累计「已认领但未到峰值」的未来峰值 | 3 槽各放行一个 item3 级 = 未来 42 GB，机器只有 23.5 GiB |
| 4 | MemAvailable 含**可回收 page cache**，会被 40–50 GB/run 的 DB 读放大，给人虚假余量 | 27 §7.5：item3 磁盘读 39.6 GB；PSI io avg10 峰值 86 |
| 5 | 运行期**不重估**：认领后到峰值前无任何检查点 | 心跳只续租，不报 RSS |
| 6 | cgroup 兜底**本机未生效**（user.slice memory.max=max；qre-worker.service inactive 且 MemoryMax=infinity） | 本文现状核查；deploy unit 写的 26G 也超过 23.5 GiB 物理，且注释自述委派可能不生效 |
| 7 | RLIMIT_AS 是**地址空间**上限，不是 RSS 上限；且代码有「VSZ 已超上限则跳过设置」守卫 | `worker/slots.py` `_apply_child_memory_limit`；AS≠RSS，作为内存兜底不可靠 |

### 3.2 建议的多重约束准入（按优先级，不是「仅靠事后 kill」）

1. **保守默认（未知策略）**：全市场/板块/未传 codes 的 `kind=full` 且无同族实测 →
   峰值预算按 **14 GB（实测最坏）/ 17.5 GB（规划值）**，**每 worker 同时最多 1 个**。
   轻任务（smoke / ≤5 显式标的，`classify_job_weight` 现口径）维持 1.5 GB 预算与
   2000MB 闸门不变——游客单股/小样本永不被全市场堵死（R2 既有目标保持）。
2. **在途峰值记账**：槽位认领前计算 `Σ已认领任务峰值预算 + 新任务预算 ≤ worker 预算
   （≈15.5 GiB，可配置）`，不满足则暂缓认领（沿用现有「暂缓领取」日志语义）。
   这把「3 个 6 GB」的静态假设换成「N 个真实峰值」的动态约束。
3. **内存闸门分级**：未知全市场任务的 MemAvailable 准入线从 6500MB 提到
   **≈15,000MB**（低于该值说明连一个最坏任务都放不下，或 PG/系统余量不足）；
   已知族任务按包络预算的动态线（预算 + PG 预留）。
4. **早停看门狗（替代「等到 RLIMIT/cgroup 杀」）**：父进程每 30–60s 采样子进程 RSS
   （/proc/<pid>/status VmRSS），超过预算 80% 且仍上升 → 主动 terminate 并落可读
   「任务超出资源配额（早停）」错误。item3 级任务在 05:55–05:57 的两分钟内就能拦下，
   相比 RLIMIT 在序列化末段才杀，可省 30–60 分钟无效计算（时间模型 §1.2：尾段占 15–20%）。
5. **修复兜底层（运维项）**：deploy unit `MemoryMax` 26G → **18G**（≤23.5 GiB 的 80%，
   合 R-MEM-001 规则 3），并验证 cgroup v2 委派真生效（本机现状是不生效）；
   子进程 `QRE_WORKER_CHILD_MEM_GB` 默认 14 → **12**（合规则 2 的 11.7 GiB，
   取整上限）——但注意这会使 item3 级任务被可读拒绝，与裁决项 1 联动。
6. **结构性修复（单独 CR，不塞进本方案）**：聚合/净值/绘图/报告/序列化分块化
   （R-MEM-001 规则 1 对「全市场×全历史」的要求本就覆盖这些阶段；item3 尾段峰值说明
   规则 1 目前只落实在计算段）。这是把 14 GB 峰值压回 12 GB 内的唯一确定路径。

### 3.3 与 P0-9 的交叉影响（必须同批考虑）

- P0-9 Required Fix 后，**截断/上传失败的全市场任务其 `/tmp` 沙箱被保留**（本地唯一完整
  副本）——每run 1.0–1.5 GiB。按 31 §3.4 的日 100 任务推演=**100–150 GB/日本地堆积**。
  容量模型必须包含这条：保留策略换成归档安全，磁盘余量必须单列（TTL/归档策略见裁决 6）。
- P0-9 分片上传落地后，20 MiB 截断仍是默认预算（§8.5 只加标记未放大预算）→ 上述
  保留路径是常态而非异常。

## 4. 与用户增长容量的关系（只引用 31 号既有模型，不新增采购/压测）

31 号公式不变：`C = J × 单任务小时数 / 24`；`worker 内存总量 = C × 单任务峰值`。
本模型对 31 号结论的**修正只有一条**：单任务峰值按策略形态分层后，**未知全市场策略的
每 worker 并发从 2 降到 1**（31 §3.1「普通策略 2 个/台」只适用于有实测的低换手族）。

| 场景（31 §3.3 口径） | 31 号建议 | 本模型修正后 |
|---|---|---|
| 日活 50，人均 1 次/日，全为普通策略 | 2 × 16GB | 不变（2/台，实测 6.3 GB 支撑） |
| 日活 50，含未知全市场策略 | 2 × 16GB | **3 × 16GB**（未知策略 1/台，需额外余量机） |
| 日活 100 | 3–4 × 16GB | 普通 4 台 / 未知策略 4 台（各 1 并发） |
| 高换手（item3 族）已实测 | 1/台 | 不变（1/台；且需先过裁决 1） |

其余扩容参数（DB 临时 2.1–2.3 GB/run、磁盘读 40–50 GB/run、产物 0.85–1.52 GB/run、
NVMe/只读副本/对象存储 TTL、screen 前置 ÷25）**全部沿用 31 号，不重算**。
本机 P0-10 结论不触发任何采购；上云时的重测义务（31 §5）不变。

## 6. 需主 Agent / 用户裁决的取舍（不自行拍板）

1. **【高风险·用户】R-MEM-001 规则 2（子进程 ≤ 物理 50% ≈ 11.7 GiB）vs 实测 13.97 GiB**：
   (a) 严格执行 → 未知全市场全期任务在分块化落地前将被可读拒绝（Availability 损失）；
   (b) 用户修订锁定要求或给「已实测策略族」例外；(c) 维持现状（已越线）——不可取。
   这决定 §5 项 5 与项 7 的排期，**必须先裁**。
2. **【产品】未知全市场全期任务是否允许直接提交**：提交闸（需先过 smoke/小样本）vs
   准入闸（照跑但 1/worker 串行）。影响排队时长与用户预期（31 号容量表按「照跑」推演）。
3. **【运维】heavy 默认 3 槽对「未知全市场」降到 1**（吞吐代价：全市场任务从 3 并发变 1），
   还是保留 3 槽但加在途记账（记账依赖项 1/3 的代码落地时间）。主 Agent 按 P0-9 发布窗口定。
